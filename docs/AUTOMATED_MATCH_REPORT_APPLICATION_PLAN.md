# Automated match-report application plan

Status: proposed implementation plan for preprod. No production deployment is authorized.

## Decision summary

1. A deterministic Python report engine is the only scoring authority.
2. The raw accumulated score adds bounded combat, assists/damage contribution, streak
   context, objectives, cap breaks, private-derived positional impact, and momentum.
3. The final display rating is calculated from that complete raw total: 100 represents
   the reference median, exceptional performances trend toward 150, and weak performances
   trend toward 50.
4. Match reports are generated by a server worker and persisted as versioned immutable
   bundles. The website reads those bundles; it does not recalculate scores in requests.
5. MCP is an optional read-only interface over the same stored reports. It is not required
   to finish a match or generate a report, and an unavailable AI/MCP service cannot block
   deterministic reporting.
6. Every full Lane B bot match must generate and validate a complete report bundle before
   the workflow can pass.

## What exists now

- `scripts/accumulation_v3.py` is the deterministic component scorer.
- `scripts/momentum_v5.py` derives a private momentum audit, a sanitized team curve, and
  bounded swing allocations.
- `scripts/build_automated_match_report.py` produces an immutable JSON/Markdown/SVG bundle,
  hashes its files, and creates a constrained optional-AI checkpoint.
- `scripts/evaluate_bot_momentum_v5.py` proves the v5 momentum engine against SQL bot
  fixtures without MySQL.
- `.github/workflows/lane-b-stats-e2e.yml` runs a real 6v6 bot match against ephemeral
  MySQL and uploads capture artifacts.
- `docs/ktpr_mcp/` contains an older season-oriented KTPR MCP proof of concept. It reads
  live data over SSH and uses a separate calculation. It is not the v5 match-report service.

The important missing link is a general database-to-v5 fact extractor and one orchestration
command. Denver currently uses a match-specific extractor; Lane B currently stops after its
capture/reconciliation report.

## Target command

All environments should invoke the same entry point:

```text
python -m ktp_report generate \
  --match-id <id> \
  --profile accumulation_v5_momentum \
  --database-url <secret/from environment> \
  --output <bundle directory> \
  --mode test|preprod|production
```

The command performs these deterministic stages:

```text
match completion
  -> snapshot match-scoped database facts
  -> validate normalized-facts schema
  -> derive private life/position and momentum evidence
  -> score all positive components
  -> apply the versioned overall-rating reference
  -> validate report schema, invariants, and privacy
  -> write immutable bundle and manifest
  -> persist report rows transactionally
  -> mark report ready for the website
  -> optionally enqueue an AI narrative review
```

The command is idempotent. Re-running the same match, code version, profile hash, reference
version, and facts hash returns the existing report identity. A changed input creates a new
revision; it never silently overwrites the prior report.

## Package boundaries

Move the reusable code into a small `ktp_report` package while retaining compatibility
wrappers for current scripts:

| Module | Responsibility |
|---|---|
| `extract.py` | Read one match from MySQL and create normalized facts. No scoring. |
| `spatial.py` | Derive per-life and momentum evidence; private output is explicitly classified. |
| `score.py` | Pure deterministic accumulation and final rating. No database/network access. |
| `normalize.py` | Load a versioned human or synthetic reference and transform complete raw totals. |
| `render.py` | JSON, Markdown, HTML fragment, and aggregate SVG rendering. |
| `bundle.py` | Hashes, manifest, schemas, privacy scan, reproducibility identity. |
| `store.py` | Transactional persistence and report revision lookup. |
| `worker.py` | Match-completion discovery, retries, locking, and status transitions. |
| `cli.py` | `generate`, `verify`, `backfill`, and `rebuild` commands. |

The scorer and renderer accept plain Python data. This keeps unit tests fast and lets Lane B,
the website worker, offline fixtures, and future MCP tools use exactly the same functions.

## Database and storage model

Do not place a large JSON calculation in the live request path. Persist queryable summary
rows plus an immutable bundle:

### `ktp_report_runs`

- `id`, `match_id`, `revision`, `status`
- `report_schema_version`, `scoring_profile`, `profile_sha256`
- `normalization_reference`, `reference_sha256`
- `code_commit`, `facts_sha256`, `report_sha256`
- `source_mode` (`test`, `preprod`, `production`)
- `started_at`, `completed_at`, `error_code`, `error_detail`
- unique identity over match/profile/reference/code/facts

### `ktp_match_player_scores`

- report run and player identity
- rank, overall rating, raw accumulated points, points per minute
- each public component total, including `momentum_points`
- observed seconds and reliability flags

### `ktp_match_momentum`

- aggregate 15-second team curve only
- sanitized swing episodes and public allocations
- no player coordinates or private routes

The complete immutable bundle (`report.json`, `report.md`, `momentum.svg`, manifest, and
optional AI files) can live on local object storage or a server directory addressed by its
SHA-256. Raw positional inputs remain in existing protected telemetry tables; private audit
bundles must use a separate non-web-accessible root with restrictive permissions and retention.

## Report lifecycle

Use an explicit state machine:

```text
DISCOVERED -> EXTRACTING -> SCORING -> VERIFIED -> READY
                              |          |
                              +-> FAILED +-> HUMAN_HOLD
```

A lightweight systemd timer can initially poll for completed, unreported matches. Later it
can be replaced by an outbox/queue without changing report semantics. Avoid a MySQL trigger:
the calculation is too large for a database transaction and retries would be opaque.

Conditions for `READY`:

- both match halves are finalized, or the match is explicitly a one-half test;
- normalized facts and final report pass their JSON schemas;
- component sums and swing-pool conservation pass;
- stable team identity survives the halftime faction switch;
- normalization reference is recorded;
- bundle hashes verify;
- public privacy scan finds no positional fields or persistent platform identifiers.

Missing evidence should create explicit `WARN`/`DISABLED` gates, not invented values. A
schema, privacy, determinism, or cross-match identity violation is a hard failure.

## Overall normalization reference

Maintain independent versioned references:

- `human_12man_v1`: qualified real 12-man matches, used for public/preprod human reports;
- `lane_b_bot_v1`: bot fixtures and full synthetic matches, used only for test assertions.

Each reference contains at minimum:

- raw accumulated points-per-minute median;
- robust log dispersion (log-rate IQR divided by 1.349);
- qualifying observation duration and match types;
- source match IDs, profile hash, build commit, creation time, and approval state.

Never normalize a bot against a human reference for a pass/fail assertion. Bots validate
plumbing, invariants, and distribution bounds; they do not calibrate human value. Until the
human reference is approved, real reports use a clearly labeled per-match provisional center
and dispersion and cannot be compared across matches.

## Website/API

The server app reads persisted `READY` revisions. Minimum endpoints:

- `GET /api/matches` — filterable match/report list;
- `GET /api/matches/{match_id}/report` — latest approved report JSON;
- `GET /api/matches/{match_id}/report/{revision}` — immutable revision;
- `GET /api/matches/{match_id}/momentum.svg` — aggregate graph;
- `GET /matches/{match_id}` — player table, component breakdown, reliability, momentum,
  and scoring explanation.

The first UI can be server-rendered HTML with the existing Markdown/SVG assets. It should
show the overall rating first, raw accumulated points second, then component totals. It must
label provisional normalization and incomplete ownership prominently.

Admin-only actions may rebuild or hold a report but must create an audit record. There is no
endpoint for editing calculated points.

## MCP and optional AI

The existing `docs/ktpr_mcp` server is useful reference code but is not complete for v5. It
uses a different season formula and direct SSH/MySQL reads. Replace or add a report MCP that
calls the application read API or report store:

- `list_match_reports(filters)`
- `get_match_report(match_id, revision="latest")`
- `explain_player_score(match_id, player)`
- `get_momentum_swings(match_id)`
- `compare_player_matches(player, match_ids)`
- `get_scoring_profile(profile_version)`

MCP tools are read-only. They return sanitized persisted artifacts and never receive database
credentials, raw positions, or permission to calculate/publish a different score.

The optional AI checkpoint runs after `VERIFIED`. AI may draft narrative, cite existing event
IDs, flag anomalies, and pose calibration questions. It cannot modify deterministic values,
quality gates, privacy classifications, or readiness. If AI is unavailable, the deterministic
report still becomes ready; the narrative remains pending.

## Required tests and CI integration

### Every pull request

- scorer unit tests for every component and overall-score conservation;
- normalization golden tests: median near 100, exceptional near 150, low near 50, bounds;
- halftime stable-team regression;
- momentum episode overlap, allocation conservation, and cap tests;
- JSON schema, manifest/hash determinism, and idempotency tests;
- public bundle privacy scan;
- API/store contract tests with a temporary database;
- fixed SQL fixture report generation with checked semantic hashes.

### Every full Lane B bot match

After `lane_b_e2e.py` completes, the workflow must run the production report command against
the same ephemeral MySQL before teardown. The workflow fails unless it produces:

- `facts.normalized.json`;
- `report.json` and `report.md`;
- `momentum.svg`;
- `manifest.json` with verified hashes;
- `report-verification.json` showing schema, sums, identity, normalization, and privacy pass.

The GitHub summary should embed the top player table and link the uploaded bundle. Upload the
entire report directory, not only the capture summary. Assertions use the synthetic reference
and broad versioned bounds, not a hard-coded winner name or exact bot ranking.

### Nightly/preprod

- one full 6v6 match exercises game -> daemon -> MySQL -> report -> bundle;
- the five Anzio SQL fixtures run through the same extractor/scorer as a fast distribution
  check;
- the pinned multi-map corpus verifies extraction and fail-closed behavior where evidence is
  absent;
- rebuild a golden report twice and require identical semantic hashes;
- serve the artifact with the application test instance and run API/link checks.

### Production readiness gate

- multiple reviewed real 12-mans complete through preprod automatically;
- a human normalization reference is frozen, versioned, and approved;
- report worker retry/recovery and duplicate-delivery tests pass;
- private filesystem and database permissions are audited;
- observed report latency and database load remain within agreed limits;
- operator signs off before enabling production match discovery.

## Implementation sequence

1. Build the general MySQL-to-normalized-facts extractor and golden fixture tests.
2. Add the unified `ktp_report generate/verify` CLI and versioned reference format.
3. Invoke it inside the existing Lane B container before ephemeral MySQL teardown; upload the
   complete bundle and make verification a hard workflow gate.
4. Add report persistence migrations, idempotent store logic, and worker state machine.
5. Add the read-only API and simple report browser.
6. Add optional read-only MCP tools backed by stored reports.
7. Run multiple preprod human matches, freeze `human_12man_v1`, then seek explicit approval
   for production discovery.

This sequence makes automated bot reporting useful immediately while keeping database writes,
the public app, MCP, AI, and production enablement as separately reviewable steps.
